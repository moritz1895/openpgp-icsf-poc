# Feature: OpenPGP Message Signing and Verification

## Feature Summary

The system creates and verifies OpenPGP digital signatures on behalf of applications that hold no private key material themselves. Producing a signature requires exactly one private-key operation — signing a locally computed digest — which is always delegated to a Hardware Security Module through the abstract Hsm-Primitives bridge; the private key never enters application memory. Verifying a signature, in contrast, requires only public key material and is always performed entirely locally, with no dependency on the HSM whatsoever. The feature supports four signature algorithm profiles: classical RSA (PKCS#1v1.5), classical elliptic-curve ECDSA, native elliptic-curve EdDSA (Ed25519/Ed448), and a post-quantum/classical composite (ML-DSA-65 + Ed25519, algorithm ID 30).

## Actors

- **Signer** — an application or service that produces a signature over a message on behalf of the party holding a pre-existing, HSM-resident private signing key. The signer supplies an opaque key handle, never raw key material.
- **Verifier** — any party checking a signature's validity. The verifier needs only the signer's public key material and never touches the HSM.

## Domain Rules

These rules apply across all use cases in this feature and constrain every use case's main and error flows below:

1. **No private signing key material ever exists outside the HSM.** As with encryption, a signing-capable private key is represented in the domain only as an opaque `PgpKeyHandle` (or, for the composite algorithm, a `PgpCompositeKeyHandle` pairing an ML-DSA-65 component handle and an Ed25519 component handle) — never as real key material.
2. **Keys are pre-provisioned, not generated by this feature.** Every key handle used for signing refers to a key that already exists in the HSM before a signing operation begins.
3. **Hashing is always computed locally.** The message digest — and, where the OpenPGP signature format requires it, the digest over the signature's own metadata trailer — is always computed with a standard, non-secret hash function outside the HSM. Only the final signing step, which requires the private key, is delegated to the HSM.
4. **Verification never involves the HSM.** Because verifying a signature requires only public key material and no secret, the entire verification use case is a local computation. No outbound infrastructure port defined by this feature is ever invoked during verification.
5. **Composite signature operations are atomic.** For the post-quantum composite profile, the two component signatures (ML-DSA-65 and Ed25519) either both succeed and are combined into one composite signature, or the whole signing operation fails. A signature containing only one valid component is never produced or accepted.
6. **Composite signature verification is fail-closed.** A composite signature is valid only if both of its component signatures independently verify against their respective public key components. If either component fails to verify — or is missing or malformed — the composite signature as a whole is invalid, never partially valid.

## Use Cases

### UC-1: Sign a Message

**Actor:** Signer

**Goal:** Produce an OpenPGP signature over a message (attached to the message, or as a standalone detached signature) that any verifier can later confirm using only the signer's public key.

**Pre-conditions:**
- The content to be signed is available.
- The signer holds a key handle for a private signing key whose algorithm is one of: RSA, ECDSA (classical curve), EdDSA (Ed25519 or Ed448), or the post-quantum composite (ML-DSA-65 + Ed25519, algorithm ID 30).
- For algorithm profiles that allow a choice of hash function (RSA, ECDSA), a hash algorithm has been selected or a default applies.

**Main Flow:**
1. The signer supplies the content to sign, the signer's key handle and algorithm, and whether the result should be an attached signature (bundled with a copy of the content) or a detached signature (standalone, alongside the original content).
2. The system computes the content's digest locally, together with the digest contribution of the signature packet's own metadata (signature type, creation time, and other bound attributes per the OpenPGP signature-hashing rules) — this step never touches the HSM.
3. The system prepares the digest for the signing operation in the form required by the target algorithm profile (for example, a PKCS#1v1.5 DigestInfo structure for RSA; a raw digest for ECDSA; the algorithm-native input form for EdDSA and for each component of the composite profile).
4. The system invokes the HSM's signing capability with the signer's key handle, the algorithm identifier, and the prepared digest. For the composite profile, this step produces two independent component signature values (ML-DSA-65 and Ed25519), each computed against the same underlying digest material; the HSM returns the raw signature value(s).
5. The system encodes the returned signature value(s) into the OpenPGP signature packet structure appropriate to the algorithm (a single value pair for RSA/ECDSA, a point encoding for EdDSA, or the dual component encoding defined by the post-quantum composite specification for algorithm ID 30).
6. The system returns the finished signature — either bundled with the content (attached) or as a standalone signature (detached) — to the signer.

**Error Flows:**
- The requested signature algorithm is not one of the four supported profiles → unsupported-algorithm error, no signature is produced.
- The signer's key handle is unknown to the HSM, or the HSM rejects it as unauthorized for signing → signing fails, no signature is produced.
- The HSM's signing operation fails for any other reason (unavailable, internal fault, malformed request) → signing fails, no signature is produced.
- For the composite profile, if either the ML-DSA-65 or the Ed25519 component signing operation fails, the whole operation fails — a signature containing only the successful component is never returned (see Domain Rule 5).
- The content cannot be fully read while computing the digest (e.g. a stream is interrupted) → signing fails before any HSM operation is attempted.

**Command Fields:** content to sign; signer's key handle and algorithm; hash algorithm selection (where applicable to the algorithm profile); attached-or-detached signature form.

**Result:** the signature — either the original content bundled with a signature packet (attached form) or a standalone signature packet (detached form) — together with the algorithm used, the hash algorithm used, the signature creation time, and the signer's key identifier.

### UC-2: Verify a Signature

**Actor:** Verifier

**Goal:** Confirm, using only public key material, that a signature over a message is valid and was produced by the holder of a specific private key.

**Pre-conditions:**
- The verifier holds the signer's public key material, matching the key identifier referenced by the signature.
- The signed message (attached form) or the original content plus a detached signature is available.

**Main Flow:**
1. The verifier supplies the signed content (or content plus detached signature) and the signer's public key material.
2. The system locates the signature packet and determines its algorithm (RSA, ECDSA, EdDSA, or the post-quantum composite) and the hash algorithm that was used.
3. The system recomputes the digest locally, exactly as during signing — over the content and the signature packet's own metadata — using only public information.
4. The system verifies the signature using only the signer's public key material, entirely locally:
   - **RSA:** PKCS#1v1.5 verification against the recomputed digest.
   - **ECDSA:** standard verification against the recomputed digest.
   - **EdDSA:** standard EdDSA verification.
   - **Post-quantum composite:** each of the two component signatures (ML-DSA-65 and Ed25519) is verified independently against its respective public key component; the composite signature is valid only if both components verify (see Domain Rule 6).
5. The system returns a valid/invalid result, together with the signer's key identifier, the signature's creation time, and any applicable warnings (for example, a hash algorithm the system considers weak).

**Error Flows:**
- No public key matching the signature's issuer key identifier is available to the verifier → the signature cannot be checked; reported distinctly from a negative (invalid) verification result.
- The signature packet is malformed, or declares an algorithm the system does not support → unsupported-format error, distinct from a negative verification result.
- The recomputed digest does not match what the signature was made over, or the cryptographic verification step fails → the result is a negative (invalid) verification outcome, not an error — this is an expected, valid business outcome of the use case.
- For the composite profile, if either component signature is missing, malformed, or fails its own verification, the overall result is invalid (see Domain Rule 6) — never a partial or component-scoped result.

**Command Fields:** the signed content (attached) or the original content plus detached signature; the signer's public key material.

**Result:** a valid/invalid outcome, the signer's key identifier, the signature creation time, and any warnings about the algorithms used.

## Domain Model Additions

- **`PgpSignature`** (entity) — a produced or verified signature: the algorithm used, the hash algorithm used, the creation timestamp, the signer's key identifier, and the encoded signature value(s) (a single value for RSA/ECDSA/EdDSA, two independent component values for the post-quantum composite).
- **`PgpSignatureVerificationResult`** (value object) — the outcome of a verification: valid or invalid, the signer's key identifier, the signature creation time, and any warnings.
- **`PgpPublicKeyAlgorithm`** (domain enumeration, shared with the encryption feature) — the signing-relevant values are `RSA`, `ECDSA`, `EDDSA`, and `ML_DSA_65_ED25519`.
- **`PgpKeyHandle`** / **`PgpCompositeKeyHandle`** (value objects, shared with the encryption feature) — used here to reference a signer's private signing key; the composite handle pairs an ML-DSA-65 component handle with an Ed25519 component handle for algorithm ID 30.

## Port Additions

**Outbound (infrastructure) ports:**
- **Signing capability** (new) — a single algorithm-agnostic capability accepting a signer's key handle, an algorithm selector (`RSA_PKCS1V15`, `ECDSA`, `EDDSA`, or `ML_DSA_65_ED25519`), and a prepared digest, and returning the raw signature value(s) produced by the HSM's private-key operation. This is the only outbound port this feature defines; no outbound port is invoked for verification (see Domain Rule 4).

**Inbound (driving) ports:**
- **Sign-message use case** — accepts content, a signer's key handle and algorithm, and a form selection (attached/detached); returns the finished signature.
- **Verify-signature use case** — accepts signed content (or content plus detached signature) and the signer's public key material; returns the verification outcome.

## Out of Scope

- HSM-side key generation of any kind for signing keys.
- Key management concerns: key discovery, keyring storage, key distribution, key certification, revocation checking, or a web-of-trust model. Callers supply public key material and key handles directly.
- The post-quantum SHOULD-level composite (algorithm ID 31, ML-DSA-87 + Ed448) and the standalone, non-composite SLH-DSA signature algorithms (algorithm IDs 32–34).
- Key certification, User ID binding signatures, subkey binding signatures, and revocation signatures — this feature covers content signing/verification only, not OpenPGP key-management signature types.
- The Cleartext Signature Framework (textual clearsign convenience format) — this feature covers binary attached and detached signatures only.

## Open Questions

1. What is the exact digest pre-processing form required for EdDSA and for each component of the ML-DSA-65 + Ed25519 composite (algorithm ID 30) — this must be confirmed against the OpenPGP signature-hashing rules before the signing capability's digest-preparation step is implemented; RSA and ECDSA pre-processing are well established, EdDSA and the composite are not yet confirmed.
2. Is the composite signing operation exposed by the HSM's signing capability as a single call producing both component signatures internally, or must the calling application service issue two separate calls (one per component) and assemble the composite signature itself? This affects whether a `PgpCompositeKeyHandle` is passed to one call or two, and must be settled before the outbound port is finalized.
3. For algorithm profiles that allow a choice of hash function (RSA, ECDSA), what are the allowed and default hash algorithms — is a fixed default (e.g. SHA-256) sufficient for this PoC, or must the caller be able to select among SHA-256/SHA-384/SHA-512?
4. Should verification reject signatures made with a hash algorithm considered weak (e.g. SHA-1) outright, or only flag them as a warning in the verification result? This PoC's cross-validation goal against standard tooling may produce test messages using either policy.
5. Since the project's interoperability testing goal includes cross-validation against standard OpenPGP tooling, should the Cleartext Signature Framework be brought into scope after all, given that some standard tools default to it for text-message signing? Currently excluded (see Out of Scope) pending confirmation this does not block interop testing.
